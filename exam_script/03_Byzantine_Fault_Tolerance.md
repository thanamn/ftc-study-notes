# Part 3 — FTC03 Byzantine Fault Tolerance (เรียงตามสไลด์)

สคริปต์ส่วนนี้เรียงตามลำดับสไลด์ของบท FTC03 ทุกหัวข้อมี `[สไลด์ N]` กำกับเพื่อให้อ่านควบคู่กับไฟล์ PDF ได้

## ทบทวน reliability แบบบริดจ์ [สไลด์ 1]

สไลด์แรกของบทนี้เป็นแบบฝึกหัดทบทวนจากบทที่แล้วครับ มันให้เครือข่ายบริดจ์ที่ประกอบด้วย R1, R2, B2, R3 และ R4 โดยที่ R1 เกิดจาก A1 ขนานกับ A2, R2 เกิดจาก B1 อนุกรม C1, R3 เกิดจาก A3 อนุกรม B3 และ R4 เกิดจาก C2 ขนาน C3 ส่วน B2 อยู่ตรงกลางพาดขวางเหมือนบริดจ์ สูตรที่ได้คือ R1 เท่ากับหนึ่งลบ (หนึ่งลบ R_A) กำลังสอง, R2 เท่ากับ R_B คูณ R_C, R3 เท่ากับ R_A คูณ R_B และ R4 เท่ากับหนึ่งลบ (หนึ่งลบ R_C) กำลังสอง

สิ่งที่สไลด์นี้สอนคือการคำนวณ R ของบริดจ์ด้วยการแจกแจงกรณีของ B2 ในตาราง ซึ่งในที่สุดได้สูตรว่า R_bridge เท่ากับ R1R2 บวก R1R2'B2R4 บวก R1'R2B2R3 บวก R1'R2B2'R3R4 บวก R1'R2'R3R4 สังเกตว่าห้าเทอมนี้คือการรวมทุกกรณีที่ระบบยังทำงาน และนี่คือตัวอย่างที่สมบูรณ์ของการใช้ MPS ร่วมกับ inclusion และ exclusion ที่เราพูดถึงในบทที่แล้ว

## Process group และสถาปัตยกรรม [สไลด์ 2–6]

สไลด์ที่สี่นิยาม process group ว่าคือกลุ่มที่สมาชิกทุกตัวได้รับข้อความที่ส่งเข้ากลุ่ม ถ้าตัวหนึ่งพังตัวอื่นรับงานแทนได้ กลุ่มเป็น dynamic ได้ และ process หนึ่งอาจเป็นสมาชิกหลายกลุ่ม แผนภาพแยกเป็นสองแบบคือ flat group ที่ทุก node เชื่อมกันแบบ fully-connected มีข้อดีว่าไม่มี single point of failure แต่ตัดสินใจซับซ้อน กับ hierarchical group ที่มี coordinator อยู่บนและ worker อยู่ล่าง มีข้อดีว่าตัดสินใจเร็ว แต่มี single point of failure

สไลด์ที่ห้าต่อด้วยสถาปัตยกรรมของกลุ่มสามแบบคือ centralized ที่มีศูนย์กลาง, decentralized ที่มีหลายศูนย์ และ distributed ที่เป็น mesh ไม่มีศูนย์กลาง และมีแถบล่างที่บอกว่าเรากำลังเคลื่อนจาก central authority ไปสู่ consensus protocol สไลด์ที่หกเปรียบเทียบ centralised ledger ที่ทุกธนาคารต้องส่งข้อมูลไปยัง clearing house กลาง กับ distributed ledger ที่แต่ละธนาคารมีสำเนาของตัวเองและเชื่อมกันแบบ peer-to-peer นี่คือภาพที่อธิบายว่าทำไม blockchain จึงเป็นเรื่องของ consensus ไม่ใช่ authority

## กฎ k fault tolerant [สไลด์ 7–8]

สไลด์ที่เจ็ดอธิบายว่าเป้าหมายของการจัดกลุ่มคือทำให้เราจัดการหลาย process เป็น abstraction เดียว และปัญหาการออกแบบที่สำคัญคือทำให้กลุ่มบรรลุข้อตกลงได้ แม้สมาชิกบางตัวเชื่อถือไม่ได้

สไลด์ที่แปดให้กฎการนับที่ต้องจำมากครับ ระบบเป็น k fault tolerant ถ้าทน fault ของ k component ได้และยังทำตามข้อกำหนดได้ ถ้า failure เป็นแบบ safe หรือ silent ต้องใช้ k บวกหนึ่ง process ถ้าเป็น arbitrary failure ต้องใช้สอง k บวกหนึ่ง process เพราะ k ตัวที่พังอาจให้ผลผิดเหมือนกันโดยบังเอิญ และถ้า process ต่าง ๆ สมคบกันให้ผลผิด ต้องใช้ทั้งหมดสาม k บวกหนึ่ง process โดยมีสอง k บวกหนึ่ง ที่ทำงานถูกต้อง ทั้งหมดสมมติว่าการสื่อสารไม่ผิดพลาด

## ปัญหา Byzantine Generals [สไลด์ 9–11]

สไลด์ที่เก้าเล่าเรื่องนายพลสองสามคนที่ต้องตกลงกันว่าจะบุกหรือไม่ โดยมีศัตรูอยู่กลาง และมีกบฏปะปน ปัญหาสองข้อคือ messenger อาจถูกจับได้และกบฏอาจโกหก สไลด์ที่สิบแสดงกรณีสามนายพลซื่อสัตย์กับหนึ่งกบฏ โดย node 3 เป็น faulty process แต่ละ node ส่งค่าของตัวเองแล้วรวมเป็น vector จากนั้นส่ง vector ให้กันและกัน แล้วแต่ละคนโหวตเสียงข้างมากในแต่ละคอลัมน์ ผลคือทุกคนเห็นชัดว่า node 3 เป็นกบฏ

สไลด์ที่สิบเอ็ดเป็นกรณีที่สำคัญครับ เมื่อเหลือสองนายพลซื่อสัตย์กับหนึ่งกบฏ มีคำเตือนสีแดงว่า algorithm does not always work และเรียกกรณีนี้ว่า Two-Army Problem เพราะเราแยกไม่ออกว่าเสียงข้างมากในแต่ละคอลัมน์คืออะไร สไลด์จึงสรุปกฎว่า ต้องมี process ที่ทำงานถูกต้องมากกว่าสองในสาม และถ้ามี process ที่พังจำนวน M ตัว ต้องมีสอง M บวกหนึ่ง ที่ทำงาน

## Oral Message algorithm และตัวอย่าง [สไลด์ 12–15]

สไลด์ที่สิบสองบอกว่า agreement บรรลุได้ด้วย Oral Messages ถ้า n มากกว่าหรือเท่ากับสาม m บวกหนึ่ง โดยมีสมมติฐานว่าทุกข้อความถูกส่งถึงอย่างถูกต้อง ผู้รับรู้ว่าใครส่ง และการไม่มีข้อความตรวจสอบได้ สไลด์ที่สิบสามให้ขั้นตอนเวียนเกิด ขั้น OM ของศูนย์ commander ส่งค่าให้ lieutenant ทุกคนแล้วแต่ละคนใช้ค่านั้นหรือใช้ค่า retreat ถ้าไม่ได้รับ ขั้น OM ของ m commander ส่งค่า ทุกคนรัน OM ของ m ลบหนึ่งโดยแสดงบทเป็น commander และสุดท้ายแต่ละคนใช้เสียงข้างมาก

สไลด์ที่สิบสี่และสิบห้าเป็นตัวอย่างที่ต้องทำได้ครับ กรณี bad lieutenant ที่ m เท่ากับหนึ่ง n เท่ากับสี่ และกบฏคือ L3 commander ส่ง A ให้ L1, L2, L3 จากนั้นใน OM ของศูนย์ L1, L2 ส่งต่อ A ส่วน L3 ส่งต่อ R ผลคือ L1 ได้ m(A, A, R) และ L2 ได้ m(A, A, R) ทั้งคู่จึงเลือกบุก กรณี bad commander นั้น commander ส่ง A ให้ L1, R ให้ L2 และ A ให้ L3 ผลคือ L1 ได้ m(A, R, A) และทุกคนก็ยังได้เสียงข้างมากเป็นบุก สังเกตว่าทั้งสองกรณีจบด้วยการที่ lieutenant ซื่อสัตย์ตกลงตรงกัน

## บทเรียนสำคัญ: จำนวนรอบต้องพอ [สไลด์ 16–19]

สไลด์ที่สิบหกถึงสิบเก้าเป็นส่วนที่สไลด์เน้นมาก และเป็นจุดที่คนมักเข้าใจผิดครับ สไลด์ที่สิบหกและสิบเจ็ดตั้งกรณี m เท่ากับสอง n เท่ากับเจ็ด โดยมีกบฏคือ L5, L6 หรือกรณีที่ commander เองเป็นกบฏด้วย สไลด์ที่สิบแปดแสดงผลลัพธ์ที่ยังผิดอยู่คือ L1 เลือกบุก แต่ L2 เลือกถอย และ L3 บุก L4 ถอย L5 บุก นั่นคือ lieutenant ซื่อสัตย์ยังเลือกไม่ตรงกัน สไลด์ถึงกับเขียนว่า Problem: All loyal lieutenants do NOT choose same action

เหตุผลที่ผิดคือเรายังสื่อสารกันไม่พอครับ สไลด์ที่สิบเก้าจึงบอกกุญแจสำคัญว่า ต้อง verify that lieutenants tell each other the same thing และจำนวนรอบต้องเท่ากับ m บวกหนึ่ง โดยรอบสุดท้ายคือ OM ของศูนย์ ที่ lieutenant แต่ละคนส่งข้อความในรูปแบบว่า L0 พูดว่า v0, L1 พูดว่า v1 ไปเรื่อย ๆ เป้าหมายคือทำให้ทุกระดับเห็นตรงกันว่าผู้ส่งพูดอะไร เพื่อไม่ให้มีคนได้ยิน A บางคนได้ยิน R เมื่อเพิ่มรอบนี้แล้ว ทุกคนจะเห็นข้อความชุดเดียวกันและใช้เสียงข้างมากในแต่ละคอลัมน์ได้ ในที่สุดจึงสรุปได้ว่า m(1A, 2R, 3A, 4R, 5A) นำไปสู่ all attack บทเรียนคือ commander ที่โกหกบวกกับกบฏสามารถพลิกเสียงข้างมากได้ ถ้าจำนวนรอบไม่พอ ดังนั้นจำนวนรอบ m บวกหนึ่งจึงไม่ใช่ทางเลือก แต่เป็นเงื่อนไขจำเป็น

## จำนวนข้อความ [สไลด์ 24]

สไลด์ที่ยี่สิบสี่สรุปว่าจำนวนข้อความทั้งหมดเท่ากับ (n ลบหนึ่ง) คูณ (n ลบสอง) คูณ (n ลบสาม) ไล่ลงไปจนถึง (n ลบ m ลบหนึ่ง) หรือเขียนเป็น big-O ของ n ยกกำลัง m ซึ่งเป็นการเติบโตแบบเอกซ์โพเนนเชียลในจำนวนกบฏ และนี่คือเหตุผลที่ขั้นตอนวิธีแบบนี้จำเป็นต้องมีทางเลือกที่ประหยัดกว่า

## Practical BFT และ Blockchain [สไลด์ 25–29]

สไลด์ที่ยี่สิบห้าแสดง practical BFT ซึ่งเป็นลำดับเวลาของข้อความห้าเฟสคือ request, pre-prepare, prepare, commit และ reply โดย client จะรอคำตอบ m บวกหนึ่ง จาก replica ต่าง ๆ ที่ให้คำตอบตรงกัน ถ้า primary เสียก็เลือกใหม่ และมีการ optimize มากมายเพื่อลด overhead

สไลด์ที่ยี่สิบหกวางกรอบ blockchain ว่าเป็นคำตอบของ BFT ที่ลบคนกลางออกไปแต่ยังให้การแลกเปลี่ยนที่เชื่อถือได้โดยอาศัย proof of work และ proof of stake สไลด์ที่ยี่สิบเจ็ดถึงยี่สิบเก้าอธิบาย proof of work ผ่านเรื่องเล่าเรื่องการแก้ไขธุรกรรมในบล็อกเก่า ถ้าใครอยากแก้บล็อกที่ 74 เขาต้องคำนวณใหม่ทั้งหมดตั้งแต่บล็อก 74 ถึง 91 ซึ่งแพงมาก และต้องทำเสร็จก่อนที่เครือข่ายทั้งหมดจะทำบล็อกที่ 91 เสร็จเพียงบล็อกเดียว สไลด์ยังแสดงการแข่งกันของนายพลที่คำนวณเวลาบุกออกมาต่างกัน แล้วใครที่ทำ proof of work เสร็จก่อนและ broadcast ก่อนก็จะชนะและบล็อกของเขาถูกต่อเข้าสู่ห่วงโซ่ นี่คือกลไกที่ทำให้ความเห็นของคนส่วนใหญ่คือโซ่ที่ยาวที่สุด

## Reliable client-server communication [สไลด์ 30–34]

สไลด์ที่สามสิบอธิบายว่าในระบบกระจาย เราต้องจัดการกับ communication failure โดย TCP ช่วยกลบ omission failure ด้วย acknowledgement และ retransmission แต่ทำงานไม่ดีเมื่อเกิด crash และมีห้าสถานการณ์ที่ต้องจัดการคือ client หา server ไม่เจอ, request สูญหาย, server crash หลังรับ request, reply สูญหาย และ client crash หลังส่ง request

สไลด์ที่สามสิบเอ็ดแสดงสามกรณีของ server ที่ crash ได้แก่กรณีปกติที่มี receive, execute, reply ครบ กรณี crash after execution ที่รับและทำเสร็จแล้วแต่ยังไม่ตอบ และกรณี crash before execution ที่รับแล้วแต่ยังไม่ทำ สองกรณีหลังนี้เองที่ทำให้เราไม่รู้ว่า request ถูกทำไปหรือยัง ซึ่งเป็นปัญหาสำคัญที่ต้องแก้ด้วย at-least-once หรือ at-most-once semantics

สไลด์ที่สามสิบสองถึงสามสิบสี่ให้วิธีแก้ทีละกรณี ถ้า client หา server ไม่เจอก็ใช้ exception handler ถ้า request หายก็ใช้ timeout แล้วส่งซ้ำโดยระวังเรื่อง idempotent operation ถ้า server crash หลังรับ request ก็สร้างใหม่แล้วลองใหม่หรือยอมแพ้ ถ้า reply หายก็ตั้ง timer และถ้า client crash หลังส่ง request จะเหลือ orphan request ซึ่งแก้ได้ด้วย extermination, reincarnation, gentle reincarnation หรือ expiration

## สมมติฐานและ HW03 [สไลด์ 35–36]

สไลด์ที่สามสิบห้ารวบสมมติฐานของการสื่อสารที่เชื่อถือได้ ได้แก่ synchronous communication, การตรวจการไม่มีข้อความได้, ทุกข้อความถูกส่งถึง, ผู้รับรู้ผู้ส่ง และลายเซ็นที่ปลอมไม่ได้และตรวจการแก้ไขได้

สไลด์ที่สามสิบหกเป็นการบ้าน HW03 ที่ให้ commander ซื่อสัตย์หนึ่งคน lieutenant กบฏสองคน และ lieutenant ซื่อสัตย์ห้าคน รวมเป็นเจ็ด lieutenant และมี commander อีกหนึ่ง รวมเป็น n เท่ากับแปด m เท่ากับสอง ซึ่งเป็นไปตามเงื่อนไข n มากกว่าหรือเท่ากับสาม m บวกหนึ่ง เพราะแปดมากกว่าหรือเท่ากับเจ็ด โครงคำตอบคือบรรยายรอบ OM ของสอง, OM ของหนึ่ง และ OM ของศูนย์ แล้วแสดงว่า lieutenant ซื่อสัตย์รวบรวมคำสั่ง Attack ได้ห้าคำสั่งเทียบกับ Retreat สองคำ จึงตัดสินด้วยเสียงข้างมากเป็น Attack


## จากคำบรรยายในห้อง [insights]

**ทำไมต้องเรียน process group** อาจารย์ปูจากคำถามว่า ระบบ process เดียวนั้นทำ fault tolerance ง่าย เพราะเราแค่ทำให้ processor ตัวนั้นมี reliability สูงพอตาม mission แต่เมื่อระบบกระจายออกเป็นหลาย process ที่สื่อสารกันด้วย message คำตอบแบบ process เดียวใช้ไม่ได้อีกต่อไป เพราะ process เดียวอาจตรวจ message ด้วย coding ได้ แต่ **กลุ่ม process ตรวจด้วย coding ทั้งหมดไม่ได้** เพราะมี process เยอะจน coding จะสิ้นเปลืองเกินไป เราจึงต้องอาศัยหลักการตรวจว่า message ไหนจริง message ไหนปลอม ซึ่งนำไปสู่ agreement และ Byzantine fault tolerance นี่คือเหตุผลเชิงเศรษฐศาสตร์ที่ทำให้เราต้องมีขั้นตอนวิธีแบบ oral message

**trade-off ของสองโครงสร้างกลุ่ม** อาจารย์อธิบายว่า hierarchical group มี "ตัวแม่" คอยสั่งตัวลูก ลดจำนวนเส้นทางการสื่อสาร (จึงตัดสินใจเร็ว) แต่**ถ้าตัวแม่เสียก็เสียทั้งกลุ่ม** ส่วน flat group ทุกตัวเท่ากัน ไม่มีใครใหญ่กว่า จึงไม่มี single point of failure แต่ทุกตัวต้อง compare/check กันเองมากขึ้น สรุปเชิงเปรียบเทียบคือ flat มัก reliable กว่าเพราะไม่ผูกกับตัวแม่ตัวเดียว

**จาก central authority สู่ consensus** อาจารย์เชื่อมภาพว่า ระบบเดิมมีศูนย์กลางตัวเดียวตัดสินใจทั้งหมด ซึ่งเทียบได้กับ server ตัวเดียวที่ต้อง reliability สูง ถ้าต้องการกระจายความเสี่ยงก็ย่อยศูนย์ออกเป็นหลายศูนย์ (decentralized) แล้วการตัดสินใจต้องใช้ consensus โดยเลือกเสียงข้างมาก และยกตัวอย่างว่า centralized ledger คือบัญชีธนาคารที่ผ่าน clearing house ส่วน distributed ledger คือฐานข้อมูลที่แชร์สำเนากันทั่วเครือข่ายโดยไม่มีศูนย์กลาง ซึ่งก็คือ blockchain

**สูตรที่ต้องใช้บ่อยคือ k+1, 2k+1 และ 3k+1** อาจารย์ย้ำหลายครั้ง และแยกให้ชัดระหว่าง **safe/silent failure** ซึ่งรองรับด้วย k+1 กับ **arbitrary (Byzantine) failure** ซึ่งต้องใช้ 2k+1 เพื่อ detect และ correct กลับมา และถ้าต้องกันไม่ให้เสียงผิดกลายเป็นคำตัดสินก็ต้องมีประมาณ 3k+1 นี่คือสูตรที่ใช้ตอบคำถามว่า "ระบบที่มี faulty m ตัวต้องมี node กี่ตัว"

**โจทย์ที่อาจารย์ให้ทำและบอกแนวข้อสอบ** คือให้เขียน Oral Message algorithm แล้วสรุปการตัดสินใจ โดยมีสองโจทย์หลักคือ commander ซื่อสัตย์กับ lieutenant 5 ตัว (มี traitor 1 ตัว) และกรณี **royal commander ส่งคำสั่งให้ lieutenant 7 ตัว ในนั้น loyal 5 ตัว traitor 2 ตัว** ให้แสดงว่า loyal lieutenant ทุกคนได้สารถูกต้องและทำตามคำสั่งได้ นอกจากนี้ตอนทบทวนโจทย์ reliability network อาจารย์ชี้ว่าสกรีมที่มี **bridge** ให้ reliability สูงกว่า เพราะ bridge ช่วยเป็นเส้นทางสำรอง

**จำนวน message ที่โตแบบเอกซ์โพเนนเชียล** คือเหตุผลที่ต้องมี practical BFT ซึ่งเลือก primary ตัวเดียว สมมติว่า primary ไม่มี fault แล้วใช้สามเฟส (pre-prepare, prepare, commit) และฝั่ง replica เพียงรอคำตอบที่ตรงกันมากกว่า m+1 ตัวก็พอ ไม่ต้องรอครบ
