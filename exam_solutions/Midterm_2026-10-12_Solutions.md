# ข้อ 1 — พื้นฐาน Fault Tolerant Computing

## 1.1 Fault Tolerant Computing ในมุมของ Safety และ Liveness

ใน **Formal Verification / concurrency theory** มีคุณสมบัติสองตระกูล

- **Safety property** = "จะไม่มีอะไรแย่ ๆ เกิดขึ้นเลย" (something bad never happens) — เป็นเงื่อนไขที่ผิดได้ทันทีเมื่อเกิดเหตุการณ์ไม่ดี
- **Liveness property** = "จะต้องมีสิ่งดี ๆ เกิดขึ้นในที่สุด" (something good eventually happens) — เป็นเงื่อนไขเรื่องความก้าวหน้า

เมื่อมอง **Fault Tolerant Computing** ผ่านสองมุมนี้

- FTC รับประกัน **Safety** ว่า ระบบจะไม่ให้ผลลัพธ์ที่ผิดออกไปอย่างเงียบ ๆ (ไม่เกิดผลลัพธ์ร้ายแรงต่อผู้ใช้/สิ่งแวดล้อม) เช่น เมื่อพังจะเข้าสู่ **fail-safe** หรือ **ไม่ส่ง incorrect output** ออกไป — ตรงกับ safety attribute
- FTC รับประกัน **Liveness** ว่า ระบบจะยังให้บริการต่อไป หรือกลับมาให้บริการได้ในที่สุด (availability / reliability / progress) — ตรงกับ availability, reliability และ recovery

**คำตอบ:** Fault Tolerant Computing คือการออกแบบให้ระบบรักษา **Safety** (ไม่ลุกลามเป็น failure ที่เป็นอันตราย โดยเฉพาะไม่ให้ erroneous output หลุดออกไป) และรักษา **Liveness** (บริการยังดำเนินต่อได้หรือกู้คืนกลับมาได้) แม้มี fault เกิดขึ้น กล่าวคือ FTC พยายามทำให้ทั้งสอง property ยังคงจริงเมื่อมี fault

## 1.2 รูปที่ 1.1 — ลากเส้นแสดง Recovery, Self-Checking และ Fail Safe

รูปที่ 1.1 คือแผนภาพ **Design Techniques**:
`System Normal State → (Specification/Implementation mistakes, External disturbances, Component defects) → Software/Hardware Faults → Errors → System failures`
มีสามโซนคั่น: **Fault Avoidance** (ก่อน fault) → **Fault Masking** (ระหว่าง fault กับ error) → **Fault Tolerance** (ระหว่าง error กับ failure)

**ตำแหน่งที่ต้องลาก/ต่อเติม:**

| สิ่งที่โจทย์ให้ | วางตรงไหน | เหตุผล |
|---|---|---|
| **Self-Checking** | ที่รอยต่อ **Fault ขั้นไปเป็น Error** (โซนต้นของ Fault Masking) — จากกล่อง Faults/Errors ลากไปยังวงจรตรวจจับที่ส่งสัญญาณ error | self-checking คือ concurrent error detection ที่ "จับ error ทันทีที่เกิด" ก่อนลุกลาม |
| **Fault Masking** | ครอบช่วง **Fault → Error** (เส้นจาก faulty component ไปยัง Error ถูกบัง ไม่ให้ไปถึง) | บัง fault ไม่ให้กลายเป็น error |
| **Recovery** | ระหว่าง **Error กับ System failures** (โซน Fault Tolerance) เป็นเส้นย้อนจาก Error กลับไปยัง Normal State | เมื่อตรวจพบ error/failure แล้วกู้ state กลับ |
| **Fail-Safe** | ที่ปากทาง **Error → System failure** ขาไปสู่ output/ผู้ใช้ (บังคับให้ผลลัพธ์ที่ออกเป็นค่าที่ปลอดภัย) | เมื่อพังต้องได้ผลลัพธ์ปลอดภัย ไม่อันตราย |

**คำตอบสั้น:** ลากเส้น **Self-Checking** จาก Faults/Errors ไปยัง checker; ลากเส้น **Recovery** ย้อนจาก Error กลับ Normal State; ลากเส้น **Fail-Safe** กั้นที่ก่อน System failures ให้ output เป็น safe state

## 1.3 Bathtub Curve — 3 แนวทางเพิ่ม Working Life (ลูกศร 1, 2, 3)

รูปที่ 1.2 แกนตั้ง = Failure rate, แกนนอน = Time แบ่ง 3 ช่วง: Infant Mortality, Working Life, Wearout

| แนวลูกศร | ผลที่ต้องการ | วิธีการ |
|---|---|---|
| **ลูกศร 1** (ดันช่วง Infant Mortality ไปทางซ้าย) | ให้ช่วงอัตราเสียเริ่มต้นสั้นลง / หมดเร็ว | **Burn-in / Screening / Stress test** ก่อนส่งมอบ, ควบคุมคุณภาพการผลิต (QC), คัดชิ้นส่วนที่บกพร่องตั้งแต่ต้นออก |
| **ลูกศร 2** (กดอัตราเสียช่วง Working Life ให้ต่ำลง) | ลด random failure rate λ ช่วงกลาง | ใช้ชิ้นส่วนคุณภาพสูง (λ ต่ำ), ลดจำนวน component, ออกแบบเรียบง่ายขึ้น, เพิ่ม **redundancy** ให้ระบบทน fault |
| **ลูกศร 3** (ดันช่วง Wearout ไปทางขวา) | ยืดเวลาก่อนสึกหรอ | **Preventive/Predictive maintenance**, **derating** ชิ้นส่วน, ระบายความร้อน, เปลี่ยนชิ้นส่วนที่สึกก่อนกำหนด (predictive maintenance) |

**สรุปคำตอบ:** 1 = คัด/burn-in ตั้งแต่ต้น; 2 = ลด failure rate ในช่วงใช้งาน (คุณภาพชิ้นส่วน + redundancy); 3 = ยืดอายุด้วยการบำรุงรักษาเชิงป้องกัน/พยากรณ์และ derating

## 1.4 รูปที่ 1.3 — Recovery Line สองแบบและประเภท

รูปที่ 1.3: 4 process P0–P3, มี message ส่งไปมา, **เกิด Fault ที่ P1 เวลา t14** ต้องลาก recovery line ย้อนกลับระยะสั้นสุด 2 เส้น

- **เส้นที่ 1: ทุก process กลับมาที่เวลา tj เดียวกัน** (`ti = tj = tk = tl`)
  ทุก process ย้อนไปที่ checkpoint คนละอัน แต่ต้องเป็น **consistent cut** ที่ลังเลได้ว่า "ทุก stress ย้อนพร้อมกัน" — เป็น **Consistent / Strongly Consistent recovery line** (ถ้าตัดแล้วไม่มี message ค้างใน transit เลย = strongly consistent)

- **เส้นที่ 2: เวลาต่างกัน ti, tj, tk, tl** (แต่ละ process ย้อนไปคนละเวลา)
  เป็นการย้อนแบบ **Uncoordinated** — **เป็น Consistent recovery line ได้** ตราบใดที่ **ไม่มี orphan message** (การรับถูกบันทึกแต่การส่งไม่) ถ้ามี orphan → **Inconsistent**

**เกณฑ์ตัดสิน (ท่องไว้):**
- ไม่มี message ค้างใน transit → **Strongly Consistent**
- มี message ค้างใน transit แต่ไม่มี orphan → **Consistent**
- มี orphan message → **Inconsistent** (ใช้เป็น recovery line ไม่ได้)

**คำตอบ:** เส้นที่ทุก process กลับเวลาตรงกัน = recovery line แบบ **consistent/strongly consistent**; เส้นที่เวลาต่างกัน = recovery line แบบ **consistent (uncoordinated)** โดยต้องตรวจว่าไม่มี orphan message ถ้ามีจะกลายเป็น **inconsistent** และต้องลาก recovery line ต้องผ่านทุก process และอยู่ **ก่อน** จุด fault (t14) เสมอ

## 1.5 รูปที่ 1.4 — Data Space และการวาง Codeword (SEC/DED)

**[ต้องดูรูป]** รูปคือกรอบจุด (grid) ที่จุดที่อยู่ติดกัน (แนวตั้ง/แนวนอน/ทแยง) มี **Hamming distance = 1** นั่นหมายความว่า การขยับหนึ่งช่องในกริด (รวมทแยง) = บิตเปลี่ยน 1 บิต ให้จุดดำหนึ่งจุดเป็น codeword แล้วเติม codeword อื่นให้ครบสำหรับ **Single Error Correction / Double Error Detection**

**หลักการ:** SEC-DED ต้องมี **minimum distance ≥ 4** (จำ: detect ต้อง d ≥ s+1; correct ต้อง d ≥ 2t+1; SEC-DED (t=1,s=2) ต้อง d ≥ 4)
ดังนั้นในกริดนี้ codeword สองตัวต้อง**ห่างกันอย่างน้อย 4 ช่อง** (นับแบบ king-move ที่ทแยง = 1)

**วิธีเติมจุดดำ:** เลือกกลุ่มจุดที่ระยะ Chebyshev (จำนวนก้าวน้อยสุดโดยขยับได้ 8 ทิศ) ระหว่างจุดใด ๆ **≥ 4** ตัวอย่างเช่นวางเป็นตารางเว้นระยะทุก 4 ช่อง (หรือรูปแบบ lattice ที่ทุกคู่ห่าง ≥ 4) ก็จะได้ SEC-DED
- ถ้าต้องการแค่ **SEC** (แก้ error 1, ไม่ต้อง detect 2) ใช้ **d ≥ 3** (ห่างกัน ≥ 3 ช่อง)
- รูปแบบง่าย ๆ คือวางจุดดำเป็น lattice ตามแนวทแยงที่เว้นช่วงสม่ำเสมอ

**ข้อควรระวัง/หมายเหตุ:** โจทย์เขียนว่า "hamming distance = 1" แต่ความหมายคือ *จุดที่อยู่ติดกัน* ห่างกัน 1 บิต (ระยะในกริด) ไม่ใช่ minimum distance ของรหัส = 1 — มิฉะนั้นจะไม่มีการป้องกันเลย ต้องตอบด้วย **minimum distance ≥ 4 สำหรับ SEC-DED**

# ข้อ 2 — Reliability Block Diagram (S0, S1, S2, S3)

ให้แต่ละบล็อกมี reliability ของตัวเองคือ **Ra** (บล็อก A), **Rb** (บล็อก B), **Rk** (บล็อก K) โดยไม่คิด reliability ของเส้นเชื่อม

> **สรุปสูตรข้อ 2.1 (แยก Ra, Rb, Rk)** — นี่คือคำตอบที่สมบูรณ์:
> - **Rs0 = Ra · Rb**
> - **Rs1 = [1 − (1−Ra)²] · [1 − (1−Rb)³]**
> - **Rs2 = Rk · [1−(1−Ra)²]·[1−(1−Rb)²] + (1−Rk) · [1−(1−Ra·Rb)²]**
> - **Rs3 = Rk²·[1−(1−Ra)³]·[1−(1−Rb)³] + 2·Rk(1−Rk)·{ 1 − [1 − (1−(1−Ra)²)(1−(1−Rb)²)]·[1 − Ra·Rb] } + (1−Rk)²·[1 − (1−Ra·Rb)³]**
>
> (ข้อ 2.2–2.5 โจทย์กำหนด **Ra = Rb = Rk = R** จึงค่อยแทนค่าแล้วแก้หา R)

## 2.1 หา Rs0, Rs1, Rs2, Rs3 (แยก Ra, Rb, Rk)

**S0 = A อนุกรม B**
```
Rs0 = Ra · Rb            (ถ้า Ra = Rb = R → R²)
```

**S1 = A ขนาน 2 ตัว แล้วอนุกรมกับ B ขนาน 3 ตัว**
```
Rs1 = [1 − (1−Ra)²] · [1 − (1−Rb)³]
    (เมื่อ Ra = Rb = R) = (2R − R²)(3R − 3R² + R³) = 6R² − 9R³ + 5R⁴ − R⁵
```

**S2 = บริดจ์ (A บน-ล่างขนาน, B บน-ล่างขนาน, K พาดกลาง)**
ใช้ **keystone conditioning บน K**
- K ทำงาน (เชื่อมจุดกลางสองฝั่ง): สำเร็จถ้า (A บน ∨ A ล่าง) ∧ (B บน ∨ B ล่าง) → `[1−(1−Ra)²]·[1−(1−Rb)²]`
- K พัง (วงจรขาด): สำเร็จถ้า (A บน ∧ B บน) ∨ (A ล่าง ∧ B ล่าง) → `1 − (1−Ra·Rb)²`

```
Rs2 = Rk·[1−(1−Ra)²]·[1−(1−Rb)²] + (1−Rk)·[1 − (1−Ra·Rb)²]
```
เมื่อ **Ra = Rb = Rk = R** → `Rs2 = 2R² + 2R³ − 5R⁴ + 2R⁵`
(ตรวจกับ state enumeration: Ra=0.9, Rb=0.8, Rk=0.95 → 0.948960 ทั้งสูตรและ enumeration ✓)

**S3 = บริดจ์ 3 สาย (A ขนาน 3, B ขนาน 3, K 2 ตัวพาดระหว่างคู่บน-กลาง และ กลาง-ล่าง)**
condition บนสถานะ K1, K2 (มี 4 กรณี):
- K1=1, K2=1: จุดกลางทั้งสามรวมกัน → `[1−(1−Ra)³]·[1−(1−Rb)³]`
- K1=1, K2=0 (หรือ K1=0, K2=1): กลุ่มที่รวมกันทำงาน **หรือ** สายเดี่ยวทำงาน (ขนานกัน)
  → `1 − [1 − (1−(1−Ra)²)(1−(1−Rb)²)]·[1 − Ra·Rb]`
- K1=0, K2=0: ไม่มีสะพาน → สามสายขนาน → `1 − (1−Ra·Rb)³`

```
Rs3 = Rk²·[1−(1−Ra)³]·[1−(1−Rb)³]
    + 2·Rk(1−Rk)·{ 1 − [1 − (1−(1−Ra)²)(1−(1−Rb)²)]·[1 − Ra·Rb] }
    + (1−Rk)²·[1 − (1−Ra·Rb)³]
```
(ตรวจกับ enumeration: Ra=0.9, Rb=0.8, Rk=0.95 → 0.990510 ✓ ; Ra=0.85, Rb=0.6, Rk=0.7 → 0.919686 ✓)
เมื่อ **Ra = Rb = Rk = R** ค่าที่ได้: R=0.5 → 0.67188; R=0.7 → 0.92514; R=0.8 → 0.97890; R=0.9 → 0.99763

> **หมายเหตุสำคัญ:** ข้อ 2.1 ต้องเขียนแยก **Ra, Rb, Rk** ตามสูตรข้างบน (นี่คือคำตอบที่ถูกต้องสมบูรณ์) ส่วนข้อ 2.2–2.5 โจทย์กำหนดให้ **Ra = Rb = Rk = R** จึงค่อยแทนค่าลงในสูตรเพื่อแก้หา R

> ค่าตาม R (คำนวณจริง): R=0.7 → S0=0.490, S1=0.885, S2=0.802, S3=0.925 ; R=0.8 → S0=0.640, S1=0.952, S2=0.911, S3=0.979

## 2.2 หา R กรณี Rs1 > 1.5 · Rs0

```
6R² − 9R³ + 5R⁴ − R⁵ > 1.5R²
→ R²(−R³ + 5R² − 9R + 4.5) > 0
→ −R³ + 5R² − 9R + 4.5 > 0   (สำหรับ R>0)
```
แก้สมการ (root): **R ≈ 0.7959**
**คำตอบ: R < 0.796** (ประมาณ 0.80) แล้ว Rs1 จะมากกว่า 1.5 เท่าของ Rs0

## 2.3 หา R กรณี Rs2 > 1.5 · Rs0

```
2R² + 2R³ − 5R⁴ + 2R⁵ > 1.5R²
→ R²(0.5 + 2R − 5R² + 2R³) > 0
→ 2R³ − 5R² + 2R + 0.5 > 0
```
root: **R ≈ 0.7647**
**คำตอบ: R < 0.765**

## 2.4 หา R กรณี Rs3 > 1.5 · Rs0

ใช้สูตร Rs3 (แบบตัวเลข) แก้ `Rs3(R) > 1.5 R²`
root: **R ≈ 0.809**
**คำตอบ: R < 0.809** (S3 ยอมรับ R ได้กว้างที่สุด)

## 2.5 สรุปควรเลือกโครงแบบใด

เรียงค่า reliability: **S3 > S2** เสมอ (ตรวจแล้ว) และ **S3 > S1** ในช่วงที่พิจารณา ดังนั้น S3 ให้ reliability สูงสุด และยอมรับค่า R ได้กว้างสุด (R < 0.809 สำหรับเงื่อนไข 1.5 เท่า)

**คำตอบ: เลือกโครงแบบ S3** (บริดจ์ 3 สาย มี K 2 ตัว) เพราะมีเส้นทางสำรองมากสุด ทน fault ได้ดีสุด และบรรลุเป้าหมาย reliability ≥ 1.5 เท่าของ S0 ในช่วง R กว้างสุด

> เกร็ด: โครงแบบ **S2 (บริดจ์เดี่ยว)** จริง ๆ แล้ว **ต่ำกว่า S1** ในบางช่วง R (เช่น R=0.8: S2=0.911 < S1=0.952) การเพิ่มบริดจ์ให้ S1 ไม่ได้ช่วยเสมอ แต่ **S3** ที่มีสามสาย + K สองตัวกลับให้ค่าสูงสุด — นี่เป็นบทเรียนว่า "จำนวนเส้นทางสำรอง" ต้องมากพอจึงจะชนะ

# ข้อ 3 — Byzantine Fault Tolerance (6 Nodes)

**โจทย์:** 6 nodes (N1–N6) N1 ส่ง A ให้ทุก node, N2 และ N3 faulty ส่ง R ตอบกลับสถานะเดียว จงแสดง Consensus Agreement (ผลคือ **Fail**)

**ตรวจเงื่อนไขก่อน (สำคัญที่สุด):**
Oral Message Algorithm บรรลุข้อตกลงได้ก็ต่อเมื่อ **n ≥ 3m + 1**
ที่นี่ n = 6, m = 2 (N2, N3) → ต้องมี 3(2)+1 = **7** แต่มีเพียง **6**
ดังนั้น **6 < 7 → ไม่ผ่านเงื่อนไข → Consensus FAIL** (แสดงให้เห็นว่าทำไมจำนวน node จึงต้อง ≥ 3m+1)

**การสาธิตว่าทำไมจึง fail (สรุปจาการรัน OM(2) ด้วยคอมพิวเตอร์):**
- **OM(2):** N1 (ซื่อสัตย์) ส่ง A ให้ N2–N6
- **OM(1):** lieutenant ทุกตัวทำเป็น commander ส่งต่อ — N4, N5, N6 (ซื่อสัตย์) ส่ง A; N2, N3 (faulty) ส่ง R
- **OM(0):** ทุกตัว relay ข้อความที่ได้ยิน

เพราะจำนวน node ไม่พอ (ต้อง 7 แต่มี 6) การ relay สร้างความกำกวมขึ้น — ผลจากการจำลอง: loyal node บางตัวตัดสินได้ไม่ตรงกับตัวอื่น (เช่น N4=N5=A แต่ N6 **ตัดสินไม่ได้** "TIE") → **loyal nodes ไม่ได้ข้อตกลงร่วมกัน = Consensus FAIL**

**คำตอบ/ข้อสรุป:**
- ด้วย n = 6, m = 2 ไม่สามารถรับประกัน agreement ได้ เพราะขัดเงื่อนไข **n ≥ 3m+1**
- ถ้าต้องการให้ทน faulty ได้ 2 ตัว (m=2) ต้องเพิ่มเป็น **อย่างน้อย 7 nodes**
- ดังนั้นระบบ 6 node นี้ล้มเหลวในการบรรลุ consensus ตามที่โจทย์ต้องการให้แสดง

> หมายเหตุ: ถ้า faulty node ถูกจำกัดให้ส่ง "R" อย่างเดียว ตลอด (ไม่ใช่ Byzantine เต็มรูป) ผลที่ได้จะ "ตกลงได้" แต่ค่าที่ได้จะผิด (ลู่เข้าหา R แทน A) ซึ่งก็ยังนับเป็นความล้มเหลวของระบบเช่นกัน แต่คำตอบหลักของข้อนี้คือ **6 < 3m+1 จึง fail**

# ข้อ 4 — Coding Theory

**[ต้องดูรูป]** ตาราง 8×6 (แถว 1–7 มีบิต 0/1, แถว 8 เป็น "?") รวมเป็น **42 บิต = 7 แถว × 6 คอลัมน์** → แบ่งเป็น **codeword ยาว 6 บิต จำนวน 7 ตัว** = Code A
> ผมไม่มีค่าบิตจริงในแต่ละช่องจากคำบรรยาย จึงให้ **วิธีทำ + ตัวอย่างที่คิดเลขให้** ผู้ใช้เติมค่าจริงจากตารางได้เลย

## 4.1 Notation ของ Code A — วิธีทำ

1. อ่านแต่ละแถวเป็น codeword ความยาว n = 6 → ได้ Code A = ชุดของ codeword ทั้งหมด (M = 7)
2. นับ **M** = จำนวน codeword (แถวที่ไม่ซ้ำ)
3. หา **d** = minimal Hamming distance: จับคู่ codeword ทุกคู่ (C(7,2)=21 คู่) คำนวณจำนวนบิตที่ต่าง แล้วเอาค่าที่น้อยสุด

**ตัวอย่าง (ถ้า Code A มี 111111 และ 111101 อยู่ในชุด):** d(111111,111101) = 1 → **d = 1**
→ Notation = **(n, M, d) = (6, 7, 1)**
ถ้าไม่มีคู่ที่ต่างกันแค่ 1 บิต ให้อ่านค่าต่ำสุดจากตาราง pairwise distance

## 4.2 ใส่ Data แถวที่ 8

เพื่อรักษาคุณสมบัติของ Code A ให้เลือก codeword แถว 8 ที่ **ระยะห่างจากทุก codeword เดิม ≥ d เดิม** (หรือ ≥ 3 ถ้าต้องการให้ตรวจจับ/แก้ error)
**วิธีทำ:** ลอง candidate 6 บิต แล้วเทียบ Hamming distance กับ codeword ทั้ง 7 ตัว เลือกตัวที่ distance ต่ำสุดมากที่สุด (เพื่อไม่ลด d)
ถ้าโจทย์ต้องการให้ code เป็น SEC ต้องเลือกให้ min distance ≥ 3; ถ้า SEC-DED ต้อง ≥ 4

## 4.3 Berger Code จากรหัสตัวหนึ่งใน A

Berger code = **separable**: นับจำนวนบิต 1 ใน data (k บิต) เขียนเป็นเลขฐานสอง แล้วต่อด้วย **bit-by-bit complement**
จำนวนบิตตรวจสอบ c = ⌈log₂(k+1)⌉; ความยาวรวม = k + c

**ตัวอย่าง:** เลือก codeword **011000** (มีเลข 1 จำนวน 2 ตัว)
- k = 6 → c = ⌈log₂ 7⌉ = 3 บิต
- จำนวน 1 = 2 = `010` (3 บิต)
- complement ของ `010` = `101`
- **Berger code = 011000 101** (9 บิต)

## 4.4 วงจร Encoding สำหรับ (10,6) Cyclic Code (g = x⁴+x³+x²+x+1)

n = 10, k = 6, r = n−k = 4; generator g = x⁴+x³+x²+x+1 = **11111**
**(10,6) code คือการเอา data 6 บิต มาคูณ/หารด้วย g แล้วได้ codeword 10 บิต**

**(ก) วิธี systematic (หารยาว — วิธีที่ใช้จริงในฮาร์ดแวร์):** เลื่อน data ซ้าย 4 ตำแหน่ง (คูณ x⁴) → หารด้วย g → เติม remainder 4 บิตท้าย

**ตัวอย่าง (data = 011000):**
- เลื่อนซ้าย 4: `0110000000`
- หารด้วย `11111` (modulo-2, บวก=ลบ=XOR): เหลือ **remainder = 1100**
- **codeword = 011000 1100 = 0110001100** (10 บิต)

ตัวอย่างอื่น: data 010101 → rem 0101 → `0101010101`; data 111111 → rem 1111 → `1111111111`

**(ข) วิธี non-separable (คูณตรง ๆ ด้วย g — "Modulo-2 Multiplier"):** codeword = data × g
- data 011000 (= x + x²) × g = x⁶ + x → **codeword = 0100001000**

**(ค) การตรวจ (decode):** เอา codeword ที่รับมาหารด้วย g ถ้า **remainder = 0** → ไม่มี error; **≠ 0** → มี error
(ตรวจแล้ว: 1111111111 หาร g ลงตัว rem=0)

**วงจร (Hardware):** ใช้ **Linear Feedback Shift Register (LFSR)** ดีกรี 4 (delay element 4 ตัว) มี XOR tap ตรงตำแหน่งที่สัมประสิทธิ์ g เป็น 1 (ที่นี่ g = 11111 → tap ทุกตำแหน่ง) — data ถูก shift เข้าไป 6 รอบแรกพร้อมคำนวณ remainder แล้ว 4 รอบสุดท้ายสลับสวิตช์ flush บิต parity ออก

**สรุปคำตอบข้อ 4.4:** เลือก data 6 บิตจาก Code A แล้วเข้ารหัสเป็น 10 บิตด้วยการหาร/คูณด้วย g = 11111 เช่น **011000 → 0110001100** (systematic) พร้อมอธิบายวงจร LFSR ดีกรี 4

# ข้อ 5 — Self-Checking Circuits

นิยาม input codespace N = 4 กรณี: (a,b,c,d) = (0,0,1,1), (0,1,1,0), (1,1,0,0), (1,0,0,1); output codeword = one-hot {(1,0),(0,1)}; (0,0),(1,1) = non-code

## 5.1 วงจรซ้าย X = AD + CD, Y = AB + BC — Fault: ขา A ของ Gate AD Stuck-at-0

เมื่อขา A ของ gate AD ค้างที่ 0 → เทอม AD = 0 → **X = CD** (เทอมอื่นไม่เปลี่ยน)

| (a,b,c,d) | ปกติ (x,y) | สถานะ | หลัง fault (x,y) | ผล |
|---|---|---|---|---|
| (0,0,1,1) | (1,0) | codeword | (1,0) | **ยังถูกต้อง (Fault Secure)** |
| (0,1,1,0) | (0,1) | codeword | (0,1) | **ยังถูกต้อง (Fault Secure)** |
| (1,1,0,0) | (0,1) | codeword | (0,1) | **ยังถูกต้อง (Fault Secure)** |
| (1,0,0,1) | (1,0) | codeword | (0,0) | **non-code → ตรวจเจอ (Self Testing)** |

**วิเคราะห์:**
- **ไม่มีอินพุตใดให้ codeword ที่ผิด** (มีแต่ codeword ที่ถูก หรือ non-code) → **Fault Secure (FS)**
- มีอินพุต (1,0,0,1) ที่ทำให้ output เป็น non-code → **Self Testing (ST)**
- **FS + ST = Totally Self Checking (TSC)** → จึงเป็น **TSC** (และเป็น SFS ด้วย ตามเงื่อนไขข้อ 1)

**คำตอบ 5.1:** อินพุต codeword ที่ยัง Fault Secure (output ยังถูกต้อง) คือ **(0,0,1,1), (0,1,1,0), (1,1,0,0)**; อินพุตที่ทำให้เกิด Self Testing คือ **(1,0,0,1)**; วงจรนี้เป็น **Totally Self Checking** (และ Strongly Fault Secure)

## 5.2 วงจรขวา X = ĀB̄CD + ĀBC̄D, Y = ĀBCD̄ + AB̄C̄D̄ — Fault: ขา C ของ Gate ĀB̄CD Stuck-at-1

เมื่อขา C ของ gate ĀB̄CD ค้างที่ 1 → เทอม ĀB̄CD กลายเป็น **ĀB̄D**

| (A,B,C,D) | ปกติ (x,y) | สถานะ | หลัง fault (x,y) | ผล |
|---|---|---|---|---|
| (0,0,1,1) | (1,0) | codeword | (1,0) | ยังถูกต้อง |
| (0,1,0,1) | (1,0) | codeword | (1,0) | ยังถูกต้อง |
| (0,1,1,0) | (0,1) | codeword | (0,1) | ยังถูกต้อง |
| (1,0,0,0) | (0,1) | codeword | (0,1) | ยังถูกต้อง |

**วิเคราะห์:**
- อินพุต codeword ทั้ง 4 ตัวให้ output **เหมือนเดิมทุกตัว** → **fault นี้ตรวจไม่เจอด้วย codeword ใดเลย**
- ดังนั้น **ไม่มีอินพุตใดเป็น Self Testing** (ST ล้มเหลว)
- แต่ output ยังเป็น codeword ที่ถูกต้องทุกกรณี → **Fault Secure (FS) ยังคงอยู่**

**คำตอบ 5.2:**
- อินพุต (Codeword) ที่สามารถเป็น **Self Testing** ได้ = **ไม่มีเลย** (fault นี้เป็น undetectable fault) จึงตอบว่า "ไม่มี"
- วงจรนี้เป็น **Fault Secure แต่ไม่เป็น Self Testing → ไม่เป็น Totally Self Checking (TSC)**
- เนื่องจาก fault เดี่ยวและ circuit ยัง **Fault Secure** (ไม่เคยให้ codeword ที่ผิด) จึงตอบว่าเป็น **Strongly Fault Secure (SFS)** — โดยนัยของนิยาม SFS สำหรับ fault เดี่ยวคือ FS บวก SFS ของเซตว่าง ซึ่งเป็นจริง
